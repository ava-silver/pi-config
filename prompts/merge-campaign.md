Trace the campaign generated by the merged PR below and merge its eligible downstream PRs. Leave PRs needing only an external team alone. For documentation changes requiring Docs review, wait for actual Docs approval before merging.

Input: $ARGUMENTS

## Trace the campaign

1. Load `git-workflow` and `repos`. Locate the source repository and read its `AGENTS.md`. Run `gh` and `gt` from the repository they target: the local shim selects organization credentials. Preserve the actual GitHub owner (`ddoghq` versus `DataDog`); do not infer it from the local directory name.
2. Confirm the source PR is merged. Record its merge SHA, inspect its diff, and use that immutable revision as the source of truth. A local checkout can be stale or lack the commit; read the file through the GitHub API at the merge SHA rather than changing the checkout.
3. Find the successful post-merge pipeline for that SHA, not the PR pipeline. For `serverless-ci`, read the root `.gitlab-ci.yml` and the campaign configuration; CI files in consumer directories run in those consumers' projects. Use `glab` to inspect the pipeline and campaign job trace.
4. Follow the workflow and run IDs from the job trace into Atlas. Use the Atlas CLI's help and read-only workflow output/history commands. Cross-check its PR manifest with the matching Slack campaign result. Distinguish this downstream run from the updater run that created the source PR.
5. Account for every configured consumer: generated PR, already merged PR, no-op, or campaign failure. Do not merge unrelated PRs with the same title or branch name. Verify provenance and current head, especially when Campaigner reuses branches.

## Review and merge

6. In each downstream repository, read its instructions and inspect the complete PR diff, current head SHA, CI, reviews, CODEOWNERS, and merge requirements. Verify generated changes against the immutable source. Use independent subagents for substantial parallel work, with each agent's working directory set to its target repository.
7. Approve changes you have reviewed when you can supply the relevant team's approval. Do not substitute your approval for an external team's or Docs approval. If only external-team action remains, leave the PR alone and record the requirement. For Docs, continue watching for actual approval; a successful approval-check workflow job does not mean its published approval status passes.
8. Wait for required checks and relevant tests. A pending `devflow/mergegate` commonly means approval is missing, not that CI fails. Separate stale canceled runs from current results, and a pending optional aggregate status from unfinished tests. Investigate actual failures through GitHub first, then GitLab job traces. Retry a verified transient failure or canceled PR pipeline through its documented mechanism; do not retry a superseded run or treat a base-branch pipeline as proof for the PR head. Do not bulk-retry canceled jobs if that includes manual release or deployment jobs.
9. Use the repository's normal merge or queue mechanism. For a direct merge, pin the reviewed head with `--match-head-commit` and use an allowed merge method. Respect an existing queue entry. Never bypass checks, use an admin override, change protection settings, or rewrite a bot's or coworker's branch. Do not publish releases or manually deploy.
10. For Docs, merge only after actual Docs approval and required checks pass. Native auto-merge is acceptable only if repository policy enforces that approval. Otherwise poll with time-bounded commands. If the session ends before approval arrives, state the remaining condition and whether a watcher is still running; do not imply indefinite monitoring.

## Report

Verify merged state through GitHub after each merge. Report concise, linked groups: merged, queued, waiting for Docs, and left to external teams or blocked. Include the source pipeline/Atlas link and any concrete failure requiring follow-up. Do not post Slack messages, request extra reviewers, or add PR comments unless needed by the documented CI/merge mechanism or requested by the user.
